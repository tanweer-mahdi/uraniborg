2. package.json

The manifest defines scripts, entrypoint, and runtime surface

Current manifest shape

{
  "name": "uraniborg",
  "version": "0.1.0",
  "private": true,
  "type": "module",
  "engines": { "node": ">=20.0.0" },
  "bin": { "uraniborg": "./dist/cli/main.js" },
  "scripts": {
    "build": "tsc --project tsconfig.json",
    "clean": "rm -rf dist coverage",
    "dev": "tsx src/cli/main.ts",
    "test": "vitest run",
    "typecheck": "tsc --noEmit --project tsconfig.json"
  }
}

What that means

  • build is compile-only, not bundle-only
  • dev runs source via tsx
  • private: true blocks npm publication as-is
  • the advertised bin must match the actual emitted path

The README already calls out that the repo emits dist/src/cli/main.js while the bin currently points at dist/cli/main.js.

Core files: package.json, README.md

3. tsconfig and tsconfig.build concepts

Uraniborg uses one TypeScript config today, and it acts as the build config

Current compiler settings

{
  "target": "ES2022",
  "module": "NodeNext",
  "moduleResolution": "NodeNext",
  "rootDir": ".",
  "outDir": "dist",
  "strict": true,
  "declaration": true,
  "sourceMap": true,
  "jsx": "react-jsx",
  "include": [
    "src/**/*.ts",
    "src/**/*.tsx",
    "tests/**/*.ts",
    "tests/**/*.tsx",
    "vitest.config.ts"
  ]
}

How to think about it

In larger repos, a split between tsconfig.json and tsconfig.build.json often separates developer ergonomics from distributable output.

  • base config: editor, tests, and shared language rules
  • build config: narrow emit set for shipped code only
  • benefit: tests and dev-only files do not leak into the release tree

Uraniborg currently does not have that split, so the single config must be treated carefully during packaging.

Conceptual takeaway: build config should be narrower than editor config.

4. What tsc emits

tsc mirrors the source tree into dist, plus declarations and maps

Emit behavior in this repo

  • rootDir: "." and outDir: "dist" preserve relative paths
  • src/cli/main.ts becomes dist/src/cli/main.js
  • .d.ts and .js.map files are emitted too
  • no bundling happens, so runtime dependencies remain external

Why this matters

The build output is a directory tree, not a packaged application. That means packaging has to decide:

  • what to copy
  • what to exclude
  • how to make the bin point to the real entry file
Common trap: assuming npm run build produces a distributable executable. It does not. It only produces JavaScript, type declarations, and source maps.
Output directory: dist/

5. Entry points

The CLI bootstrap is thin, but it controls the launch shape

Main bootstrap

src/cli/main.ts
  - parses argv
  - detects interactive TTY vs non-interactive mode
  - launches Ink when appropriate
  - otherwise dispatches to Commander

src/cli/program.ts
  - defines commands
  - registers handlers
  - prints the help/usage surface

Runtime launch model

  • uraniborg in an interactive TTY opens the Ink dashboard
  • --no-ui bypasses Ink and keeps plain CLI execution
  • stdin/stdout TTY state decides whether interactive UI is even attempted

Why packaging cares

The bin file is not just a launcher. It is the first step in deciding whether the user gets a terminal app, a plain CLI command, or a compatibility path.

6. Bin wiring and dist layout

The biggest current packaging pitfall is path drift

Current mismatch

package.json
  "bin": {
    "uraniborg": "./dist/cli/main.js"
  }

tsconfig.json emit
  src/cli/main.ts -> dist/src/cli/main.js

Consequence

  • npm link and packaged installs point to the wrong file
  • README examples use the emitted path, not the advertised bin
  • release artifacts need a deliberate alignment step

If the path mismatch ships, the package looks installed but the command fails at startup.

What a healthy release needs

  • bin path matches emitted file path exactly
  • build output is checked before publish
  • an installed-package smoke test resolves the actual entrypoint
Read the mismatch note in README.md.

8. Common packaging pitfalls in this repo

What can go wrong when packaging this codebase

Repo-specific pitfalls

  • bin path mismatch between manifest and emit output
  • no release pipeline to validate installed-package behavior
  • tests in the emit graph because the build config includes them
  • no files allowlist, so a publish/archive strategy is undefined
  • external runtime dependency on a compatible feynman

Cross-platform concerns

  • shell scripts and path assumptions in docs may be Unix-centric
  • Windows needs correct entrypoint resolution and spawn behavior
  • native packaging options change the maintenance surface sharply

Cross-platform portability is easier at the Node layer than at the distribution layer.

Pitfall checklist should be part of release gates.

9. Recommended release workflow

A sane packaging flow for Uraniborg

Minimum release sequence

  1. build with npm run build
  2. run npm run test and npm run typecheck
  3. verify the emitted entrypoint path
  4. smoke-test the installed bin on macOS, Linux, and Windows
  5. confirm the runtime contract for Feynman/Pi is documented

Decision points to settle before shipping

  • npm package vs archive bundle vs single executable
  • whether Feynman/Pi is a bundled dependency or a host prerequisite
  • whether tests are excluded from shipped artifacts
The repo is closest to a cross-platform Node distribution, but it is not yet a fully self-contained standalone runtime bundle.
For release, keep the build artifact and bin path in lockstep.
